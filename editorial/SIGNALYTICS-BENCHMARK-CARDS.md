# Signalytics Business Benchmark Cards — evidence-rich editorial overlay (v1)

**적용 범위:** `signalytics.news`의 비즈니스 카드뉴스에만 적용. 공통 `BUSINESS-IDEA-MAGAZINE.md`, `business-idea-magazine.v1.json`, 카드/이미지 품질 규칙을 보완하지만, 다른 Instagram 계정이나 `suengj-style` 및 전역 voice에 영향을 주지 않는다.

**목표:** “실제 회사 두 곳이 있다”는 소개를 넘어, **A/B 각각의 실제 거래 구조, 지불자, 수익 구조, 비용·운영 제약, 결정적 차이, 국내 실험 가설**을 독자에게 전달한다. 조사와 서술을 먼저 완료한 다음 시각화를 시작한다. 자격 없는 ‘성공 사례’, 성과 과장, 시장 공백 단정은 하지 않는다.

## 1. 주제와 벤치마크 사례 선정

1. 기존 사업 아이디어 Sheet의 원본, 클러스터/원리, 최신 기업 및 게시 이력을 참조한다. 아이디어는 검증 데이터가 아니라 씨앗이다.
2. 비교 질문을 한 문장으로 특정한다: **어떤 고객이 어떤 문제에 지불하며, A/B는 해당 거래와 운영 마찰을 어떻게 다르게 해결하는가?**
3. 실제 운영되는 **서로 다른 두 회사 A/B**를 찾고 `same_model`(동일 핵심 메커니즘) 또는 `adjacent`(유사하지만 다른 부분이 있음)를 표시한다. 같은 회사 하나를 두 개 사례처럼 포장하거나 단지 업종만 같은 회사를 억지 비교하지 않는다.
4. 등록 후보 최대 3개 안에서 신뢰할 수 있는 근거가 있는 기업을 택한다. 두 사례가 부족하면 **아이디어 자체를 교체하거나 부분완료**한다. 뉴스 검색 결과의 짧은 미리보기만으로 기업의 수익성·지불 조건을 단정하지 않는다.

## 2. 회사 A/B 필수 팩트시트

이미지 원고 이전에 회사별로 다음을 확인한다. 미공개는 미공개, 찾지 못한 사실은 확인 불가로 표시한다. 알려진 기업 ‘성공’이나 ‘성장’을 근거 없이 전제하지 않는다.

| 동일하게 조사할 축 | 구체적인 질문 |
|---|---|
| 제품·고객·지역 | 공식 제품/서비스명, 누가 쓰는가, 해결하는 반복 문제(JTBD), 실제 서비스 지역 |
| 거래/이용 흐름 | 고객 유입→탐색/매칭→구매/이용→결제/완료, 공급자 참여와 실제 서비스 단계 |
| 지불자·과금 방식 | 누가 언제 무엇에 돈을 내는가, 수수료/구독/광고/라이선스의 확인된 과금 방식 |
| 가치와 운영 | 거래에 필요한 재고·공급 확보·물류·신뢰/검수·CS·규제 중 무엇을 실제로 운영하는가 |
| 비용 및 확장 제약 | 비용·보조금·리드타임·영업·채널·지역 제한·환불/정산 중 구조적 병목 |
| 획득·반복 이용 | 공식 자료에서 확인된 유입 채널/파트너·리텐션/재구매 메커니즘(실적은 별도 검증) |
| 실적/시장 수치(있으면) | 공시·확인된 값, 기간·통화·지역·단위·측정 대상을 명시. GMV/매출/이익 분리 |
| 경쟁우위·취약점 | 관찰된 차이와 분석자의 추론을 분리. 검증되지 않은 ‘시장 지배’ 표현 금지 |

**사례 채택 최소 기준:** A/B 각 회사에 대해 최소 **직접 확인한 공식 원문 1개 + 출처에 매핑된 중요한 사실 3개**를 확보한다. 사실 중 적어도 한 개는 **실제 거래/지불/운영 메커니즘**이어야 한다. A/B 사이 비교 가능한 **공통 축 5개 이상**을 확보한다(부분 공개는 ‘미공개’ 명시). 이 기준을 억지로 맞추기 위해 사실을 발명하지 말고 사례를 교체하거나 부족한 범위를 드러낸다. 성과/시장점유율/우수성 주장은 주장 수준에 맞는 공시·독립 근거가 없으면 쓰지 않는다.

각 주요 사실에는 claim ID, 원문 URL·문서명·발행일(없으면 null)·열람일·관련 국가/기간/단위·`fact/analysis/assumption`의 구분을 남긴다. 공식 홍보자료의 수치는 ‘기업 발표 기준’임을 표시한다. 출처 링크의 존재만으로 주장이 입증되었다고 추정하지 않는다.

## 3. 비교 분석: 결과물이 회사 소개 두 편이면 실패

동일한 축 **5개 이상**으로 A/B를 비교하고, 관찰된 **구조적 차이 2개 이상**을 찾는다. 예를 들어 고객/과금/공급 동선/운영비용/유통 파트너/지역 및 규제 제약을 대조한다. 각 차이에 대해 **사실 → 왜 이런 모델을 택했는지(분석) → 어떤 트레이드오프가 있는지 → 우리의 실험에 의미하는 바**를 한 흐름으로 설명한다.

두 기업 모두 ‘플랫폼으로 연결한다’, ‘고객 편의를 높인다’ 수준의 문구를 쓰는 것은 실패다. 단지 기업명이 다르다는 이유로 동일 문장을 두 장에 반복하지 않는다. 서로 다른 지역·제품·성장단계의 GMV·매출·영업이익을 분모/기간 구별 없이 직접 비교하지 않는다. 실적이 없더라도 **실제 서비스 구조·결제 경로·운영 난제**를 깊게 비교할 수 있다.

## 4. 카드 구조 — 기본 5장, 필요시 6장

기존 고정 다섯 frame ID `cover → money → case-a → case-b → opportunity`는 유지한다. **Signalytics에서는 A와 B가 반드시 서로 다른 회사**여야 하며 일반 business magazine의 한 회사 deep-dive fallback을 사용하지 않는다. 6장은 실제로 의미 있는 최신 변화·뉴스가 실험 결론에 영향을 줄 때만 Trend로 허용한다.

| 장 | 독자의 질문 | 필수 정보 |
|---|---|---|
| 1 표지 | 왜 이 아이디어인가 | 문제·고객·지불 가치·핵심 사업 가설 한 문장. 추상 슬로건만 금지 |
| 2 돈의 흐름 | 누가 돈을 내고 어디서 비용이 발생하나 | 실제 가치 흐름과 결제/수익 흐름을 분리, 핵심 지불자와 운영비용 1–2개 |
| 3 Benchmark A | A는 어떻게 작동하나 | **검증된 실제 고객/거래 동선/과금/운영·비용 요소 3–4개**, 기업/출처 표시. 기업 프로필만 금지 |
| 4 Benchmark B & 차이 | B는 A와 어떻게 다른 선택을 했나 | B의 **동일 항목 3–4개**와 **A↔B 차이 2개**(왜 중요한지 짧게). 회사명만 바꾼 소개 금지 |
| 5 기회/첫 실험 | 우리가 어떤 문제부터 검증해야 하나 | A/B에서 취할 원리 각 1개, 복제하면 위험한 제약 1개, 좁은 고객군·MVP 행동·측정 지표/중단 조건 |
| 6 Trend (조건부) | 최신 변화가 사업 가설을 바꾸나 | 실제 사건/발행일/출처/전파 경로와 가설 영향. 보충용 뉴스 나열 금지 |

카드마다 **핵심 메시지 하나 + 근거가 다른 약 3개 정보 단위**를 목표로 한다. Benchmark A/B가 로고·창업연도·업종만 보여주면 반려한다. 필수 정보가 많아도 글씨 크기부터 줄이지 않는다. 정보 위계를 만들고, 핵심만 카드에 남기며 상세 근거는 아래 독자용 `benchmark-brief.md`로 분리한다. 단, **카드 3/4장의 실제 거래와 운영 메커니즘, 비교 차이 2개는 카드에서 빼면 안 된다.**

출처 표시는 카드에 짧게, URL과 기준시각은 캡션과 벤치마크 원고에 완전하게 남긴다. 판단을 바꿀 만한 제약(미공개 수익, 제한 지역, 단순 가정)은 카드에 직접 적는다. 광고·홍보 카피처럼 보이는 과장된 확정 문구를 사용하지 않는다.

## 5. 독자용 추가 산출물 `benchmark-brief.md`

리서치가 카드 압축 과정에서 사라지지 않도록 하나의 **완성 한국어 Markdown**으로 첨부한다. 섹션은 다음과 같다.

1. 비교 질문 및 핵심 결론(닮은 점, *실제 구조가 갈리는 지점*, 판단 조건).
2. A/B 각각의 팩트시트: 제품·사용자 동선·지불자/수익/비용·유통·실행 제약·공식 근거/기준일.
3. 동일 축 **5개 이상의 대조표**: 관찰 사실과 분석적 해석/미공개를 구분.
4. 근거가 있는 차이 **2–3개의 트레이드오프**: 무엇을 따라 할 수 있고 무엇은 그대로 복제할 수 없는가.
5. 국내 적용: 기존 경쟁/규제·공급/가격 문제를 확인한 것과 **추정 중인 것**을 분리. ‘한국에는 없다’ 단정 금지.
6. 첫 MVP 검증: 좁은 고객군·핵심 가설·실험 절차·측정 지표·중단/반증 조건. 수치 목표는 실적이 아니라 **검증 전 가설**로 표기.
7. 사실별 출처 URL·제목·발행/열람일·조건. 추론·가정은 라벨 부여.

**benchmark-brief.md가 카드의 빈약함을 용인하지는 않는다.** 카드 안에서 A/B의 작동 방식과 차이가 실제로 전달되어야 한다. `caption.md`는 자연스러운 본문/요점/출처를 제공하되 사실을 축소하지 않는다.

## 6. 시각자료, 출력과 현재 저장 경계

실제 로고·상품·서비스 화면은 공식 원본과 사용 조건 확인 후에만 포함한다. 원본을 생성 이미지로 ‘재현’해 실제 사례처럼 쓰지 않는다. 확보 불가 시 정확한 회사명 텍스트나 명시된 도식으로 대체한다. 일반 장면 일러스트·사진에는 라벨을 붙이지 않는다. 가짜 UI·제품 화면·로고·데이터처럼 실제 자료로 오인될 수 있는 경우에만 plan의 `mockup_risk: true`를 지정하고 ‘연출 이미지’ 또는 ‘ILLUSTRATIVE / 가상 예시’를 표시한다.

사진을 문구 아래 배경으로 크롭하면 `focal_box`와 `focal_min_area_ratio`를 plan에 기록한다. 표시 영역이 얼굴 또는 핵심 사물 전체를 포함하고 최소 면적 비율을 충족해야 한다. 실패하면 사진과 문구를 분리한 split 레이아웃으로 바꾸고, split도 실패하면 R7 일러스트를 사용한다.

**사람 편집자 카드 QA:** (1) AI 요약처럼 읽히는가 — 요약체 종결, 명사구 나열, 일반적인 전환 문구를 확인한다. (2) 크롭이 의미 있는가 — 얼굴 또는 핵심 사물 전체가 보이는가. (3) 라벨이나 푸터가 불필요하지 않은가.

**Signalytics 최종 전달:** 현재 채팅에 개별 최종 PNG 5장(근거 있는 6장), `caption.md`, `benchmark-brief.md`를 **실제 파일**로 첨부한다. 별도 preview/ZIP은 실제 가능한 경우에만 제공한다. 프롬프트, JSON 또는 존재하지 않는 파일 링크를 이미지 납품으로 주장하지 않는다.

**Signalytics 결과물의 Google Drive 폴더 생성·업로드·readback은 수행하지 않는다.** 이는 해당 시리즈의 출력 정책이며, 다른 Registry batch의 Drive 결과 저장 계약을 바꾸지 않는다. 기존 승인 스타일/로고 등 **Drive의 읽기 전용 참고자료** 조회는 그대로 허용한다. 기존 허용된 사업 아이디어 Sheet의 `07_실제사례`/`08_업로드 내용` 이력은 관리할 수 있으나, Drive 이미지 ID가 없다면 비워두고 **확인 가능한 Chat 산출물/내용 상태만** 남긴다. Sheet 쓰기 실패를 이미지 자체 생성 실패로 가장하지 않는다. 첨부의 장기 지속·다른 대화 접근을 보장하지 않는다.

동일 콘텐츠 재시도 시 Sheet content_id와 실제 접근할 수 있는 원본/첨부를 확인한다. 파일에 접근할 수 없으면 ‘이전에 생성됨’을 파일 확인으로 둔갑시키지 않는다. 성공 상태는 `벤치마크 조사` → `완성 원고` → `PNG 생성/실제 bytes` → `채팅 전달` → `사용자 수락`으로 각각 판단한다. 원고 성공만 있으면 이미지 단계는 PARTIAL/NOT_RUN로 보고한다.

## 7. 검수·반려 기준

- 서로 다른 실제 회사 두 곳의 **직접 읽은 공식 근거·각 3개 핵심 사실**이 없거나, A/B 공통 비교 축 5개와 구조적 차이 2개가 없다.
- 카드 3/4가 회사 소개만 하거나, 두 회사의 실제 지불/서비스 운영 메커니즘을 설명하지 않는다.
- ‘누가 돈을 낸다’와 ‘어떤 비용이 든다’가 사라졌다. GMV/매출/이익, 기업 주장/독립 관찰, 수치 기준 기간을 혼동한다.
- 기회 카드가 국내 시장의 공백·수익성을 이미 증명된 것으로 말하거나, 고객 검증의 첫 실험/실패 조건이 없다.
- 세부 근거가 전부 별도 보고서에만 있고 **카드는 정보가 부족**, 또는 글씨가 너무 작아 390px 모바일 미리보기에서 읽을 수 없다.
- 출처·숫자·화살표·회사명·로고/화면 출처가 불확실하다.
- Signalytics 결과 업로드 실패 때문에 채팅 결과를 폐기하거나, 이미 제거된 Google Drive 저장 경로를 실행한다.

이 문서는 **편집 계약**이다. 이미지/검증/Chat 전달의 실제 성공은 매번 별도로 증명해야 한다. 공개 게시나 사용자 승인도 자동으로 발생하지 않는다.
